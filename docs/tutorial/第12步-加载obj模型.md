## 二、`.obj` 是个纯文本格式，但坑不在文本上

`.obj` 读进来其实只有四种有意义的行：

```
v   1.0 0.5 -0.3     顶点位置（vertex）
vt  0.25 0.75        贴图坐标（texture coordinate）
vn  0.0 1.0 0.0      法线（normal）
f   1/1/1 2/2/2 3/3/3   一个面（face），每个角写成 v/vt/vn
```

剩下的 `o` / `g` / `s` / `usemtl` / `mtllib` / `#` 注释，本项目**一律忽略**。文本解析本身没什么可讲的（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L86-L119) 就是一个 `while (getline)` 加一串 `if (tag == ...)`）。

真正的坑全在**语义**上，一共三个，下面按「容易踩到的顺序」讲。

### 2.1 三条索引流，各自独立编号

这是新手第一个会写错的地方：

> **`v`、`vt`、`vn` 是三条互不相干的编号流，各自从 1 开始独立编号。**

一个角的 `f 5/2/9` 意思是：位置取第 5 个 `v`、UV 取第 2 个 `vt`、法线取第 9 个 `vn`。这三个数字之间**没有任何对应关系**——不是「同一个顶点的三种属性」，而是三个独立表里的下标。

[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L78-L83) 就是照这个理解存的：三张表分开存。

```cpp
std::vector<Vec3> positions;   // 对应 v
std::vector<Vec2> uvs;         // 对应 vt
std::vector<Vec3> normals;     // 对应 vn
```

### 2.2 1 基，而且允许负数（从末尾倒数）

OBJ 的下标是 **1 基**（第 1 个 `v` 是下标 1），而且**负数表示从末尾往前数**：

| 写法 | 含义 |
| :---: | :--- |
| `1` | 第 0 个 |
| `n` | 第 n-1 个 |
| `-1` | 最后一个 |
| `-2` | 倒数第二个 |

[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L29-L34)：

```cpp
int resolve_index(int raw, int count)
{
    if (raw > 0)  return raw - 1;      // 1 基 → 0 基
    if (raw < 0)  return count + raw;  // 从末尾倒数
    return -1;                          // 0 或没写，表示「这一角没这个属性」
}
```

负数索引在「用文本编辑器手工拼出来的 OBJ」里很常见，读进来看见 `f -1 -2 -3` 别慌，就是这个意思。

### 2.3 一个角有四种写法

`f` 的每个角不一定三项都写，四种写法都要认（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L37-L63)）：

| 写法 | 含义 |
| :--- | :--- |
| `f 1 2 3` | 只有位置 |
| `f 1/4 2/5 3/6` | 位置 + UV |
| `f 1//7 2//8 3//9` | 位置 + 法线（UV 空着，注意是**两个斜杠**） |
| `f 1/4/7 2/5/8 3/6/9` | 全都有 |

`v//vn` 这种「中间空一段」的写法是最容易崩的：按 `/` 切出来中间是个**空字符串**，直接丢给 `atoi` 会得到 0，就把 UV 索引悄悄变成了「没有」。所以切开之后要判空：

```cpp
const std::string vt = token.substr(first + 1, second - first - 1);
if (!vt.empty()) {
    ref.vt = std::atoi(vt.c_str());
}
```

### 2.4 缺斤少两要兜住

真实 `.obj` 文件经常不完整。本项目定的容错规则（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L161-L168)）：

- **缺 `vn`**（法线）：用「这个面自己的法线」现算 —— 结果就是**平面着色**（每个面一个法线，棱角分明）。
- **缺 `vt`**（UV）：填 `(0,0)`。
- **多边形面**（4 个及以上的角）：以第 0 个角为扇心，扇形三角化。

### 2.5 多边形 → 三角形：扇形三角化

`f` 不保证是三角形，可能是四边形、五边形。GPU 只认三角形，所以要拆。

本项目用最简单的**扇形三角化**：固定拿第 0 个角当扇心，和后面每两个相邻点组一个三角形（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L170-L172)）：

```
一个 5 边形  p0 p1 p2 p3 p4
拆成 3 个三角形： (p0,p1,p2) (p0,p2,p3) (p0,p3,p4)
```

对**凸多边形**这个拆法一定对；凹多边形会拆出错误结果，但那是另一个话题（真实渲染器里会走更严谨的三角化），本项目先不管。

### 2.6 三张表 → 一张表：vertex de-indexing

这是本步**最核心的一步**，也是最值得单独拎出来讲的一步。

OBJ 里顶点是「三条独立索引」，而我们的 `Mesh`（以及所有 GPU）要的是「**一个顶点 = 位置 + UV + 法线绑在一起的单一索引**」。这两个形态不一样，中间要做一次转换：

> 把 `(v, vt, vn)` 这个**三元组**当 key 去重。同一个三元组第二次出现，就复用第一次生成的顶点下标。

代码就是一张 `map` + 一个循环（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L133-L192)）：

```cpp
std::map<std::tuple<int, int, int>, int> vertex_map;   // (v, vt, vn) → 新顶点下标

// ... 对每个三角形的每个角：
const auto key = std::make_tuple(c.v, c.vt, vn_key);
auto it = vertex_map.find(key);
if (it != vertex_map.end()) {
    out.indices.push_back(it->second);   // 见过 → 复用
    continue;
}
const int new_index = static_cast<int>(out_pos.size());
out_pos.push_back(positions[c.v]);
out_uv.push_back(c.vt >= 0 ? uvs[c.vt] : Vec2(0.0f, 0.0f));
out_nrm.push_back(c.vn >= 0 ? normals[c.vn].normalize() : face_normal);
vertex_map.emplace(key, new_index);
out.indices.push_back(new_index);        // 没见过 → 新建
```

这个过程行话叫 **vertex de-indexing → re-indexing**（解绑再重新绑定），**每一个模型加载器都要做**，Unity / Unreal / Assimp 内部都一样。

> 为什么「绑定在一起的属性」和「分开的属性」不能等价——一个立方体只有 8 个位置，为什么最后要展开成 24 个顶点？见 [十、原理深挖](#十原理深挖三个卡点) 的 10.1。

**为什么它不影响美观，但影响正确性**：位置相同的两个角，如果一个带 UV `(0,0)`、另一个带 UV `(1,0)`（比如立方体一个角上，三个面各要一份不同的 UV），它们**必须**是两个顶点。合在一起就会有一个面贴图错的。这就是「顶点 = 属性的组合，不只是位置」。

### 2.7 OBJ 的 `vt` 要翻转一次

OBJ 的贴图坐标约定是「**原点在左下角、v 向上**」；本项目 `Texture` 是「**原点在左上角、v 向下**」（见 [texture.hpp](file:///d:/SDL_project/softbymyself/src/core/texture.hpp#L11-L15)）。两个约定没有对错，但必须换一次，否则贴图上下颠倒（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L97-L103)）：

```cpp
} else if (tag == "vt") {
    float u = 0.0f, v = 0.0f;
    in >> u >> v;
    uvs.emplace_back(u, 1.0f - v);   // ← 就翻这一下
}
```

> 这条「约定差」为什么容易被忽略，以及不翻会怎样，见 [十、原理深挖](#十原理深挖三个卡点) 的 10.3。

## 三、`Mesh`：把「模型」抽成一个数据结构

第 12 步之前，每个模型的顶点表直接写在 `main.cpp` 里（`const Vec3 cube_positions[36] = {...}`）。那是「一个模型一段硬编码」，想换模型得重抄一遍。

`Mesh` 把这件事抽出来（[mesh.hpp](file:///d:/SDL_project/softbymyself/src/scene/mesh.hpp#L27-L44)）：

```cpp
struct Mesh {
    std::vector<Vec3> positions;   // 模型空间位置
    std::vector<Vec3> normals;     // 模型空间法线（单位向量）
    std::vector<Vec2> uvs;         // 贴图坐标，(0,0) 在左上角、v 向下
    std::vector<int>  indices;     // 拍平的三角形索引表，每 3 个一组
    Aabb              bounds;      // 模型空间包围盒，加载完立刻算

    int vertex_count()   const { return static_cast<int>(positions.size()); }
    int triangle_count() const { return static_cast<int>(indices.size()) / 3; }
    bool empty()         const { return positions.empty() || indices.empty(); }
};
```

**为什么用索引（`indices`）而不是每个三角形直接写三个顶点**：一个 861 顶点的圆环展开后要写 1600×3 = 4800 个顶点，其中大量重复。用索引则顶点只存一份，三角形只存下标 —— 省内存，而且顶点着色只算一次。这就是渲染管线上「**图元装配（Primitive Assembly）**」那一步要的数据形态。

**为什么索引拍成一维 `std::vector<int>` 而不是 `int[][3]`**：可以直接塞进 `std::vector`，也能和「先读进来到处 push_back、读完再统计数量」的流程配合（OBJ 加载就是这个流程）。代价是渲染函数拿到的参数从 `const int (*)[3]` 变成了 `const int*`，要自己 `indices[t*3 + 0..2]` 地取（[renderer.cpp](file:///d:/SDL_project/softbymyself/src/render/renderer.cpp#L199-L201)）。

## 四、踩坑记录：圆环上一条莫名其妙的暗带

**这一步最值钱的记录。**

### 4.1 现象

圆环模型加载出来，贴图整体是对的，但在环面某一条「经线」上，出现一条**很宽的暗带**（贴图在那个位置被压扁成一条脏色）。球体上对应的是两极附近的一条环带。

### 4.2 根因：循环曲面少生成了「最后一圈」

圆环是**循环**的：绕一圈回到起点。生成顶点时如果只生成 `0 .. seg-1` 列，那么：

- 第一列的 `u = 0.0`
- 最后一列的 `u = (seg-1)/seg = 0.975`

而**最后一列和第一列在几何上是挨着的**（转一圈接上）。于是夹在这两列之间那一圈三角形，拿到的 `u` 是从 `0.975` 直接**跳回** `0.0`——在 UV 空间里这是**倒着走了 0.975 个贴图宽度**，也就是把那整张贴图**反向采样**了一遍。表现就是那一圈特别脏、特别暗。

### 4.3 修复：循环方向多生成一圈

在生成器里，把循环方向的顶点数从 `seg` 改成 `seg + 1`（[gen_obj_models.py](file:///d:/SDL_project/softbymyself/tools/gen_obj_models.py#L62-L70)）：

```python
# ⚠ 接缝：循环方向的最后一列/行要「重来一次」，让 u/v 能到 1.0。
#   如果只生成 0..seg-1，最后一列 u=0.975、第一列 u=0.0，它们之间的三角形
#   会把整张贴图反向采样一遍 —— 表现为模型上一条很明显的暗带。
#   多生成一圈（位置和第一列重合、但 u=1.0），就变成正常的贴图接缝。
for i in range(major_seg + 1):
    ...
    uvs.append((i / major_seg, j / minor_seg))   # 最后一圈 i = major_seg → u = 1.0
```

注意关键点：**多加的那一圈，位置和第一圈重合（`i % major_seg` 让角度绕回来），但 UV 是 `1.0` 而不是 `0.0`**。

于是那一圈三角形两边分别是 `u = 0.975` 和 `u = 1.0`——正常的、只有 0.025 宽的一列，贴图不再倒流。接缝从「一条脏带」变成了「一条正常的贴图边界」。

球的 `u` 方向同理（[gen_obj_models.py](file:///d:/SDL_project/softbymyself/tools/gen_obj_models.py#L93-L102)）。

> 为什么「多一排位置重合、UV 不同的顶点」是**唯一正确**的解法（而不是把 u 钳到 1.0，或者把贴图设成 clamp）——见 [十、原理深挖](#十原理深挖三个卡点) 的 10.2。

### 4.4 教训

- **循环曲面的顶点数不是 `seg`，是 `seg + 1`。** 这是一条会反复用到的东西：圆环、球、圆柱、管状体……凡是「绕一圈接回自己」的方向，都要多生一排。
- **症状（一条脏带）和原因（UV 倒流）隔得很远**，光看画面猜会被带偏。这时候回去看**生成 UV 的那几行代码**，比盯着渲染器强。

## 五、顺手拆掉的一个隐患：`kMaxVertices` 静默截断

第 11 步的 [renderer.cpp](file:///d:/SDL_project/softbymyself/src/render/renderer.cpp#L184-L190) 里有这么一行（改之前）：

```cpp
ClipVertex clip_vertices[1024];   // ← 写死上限，超了静默截断
```

手写立方体只有 36 个顶点，看不出问题。但从第 12 步起几何数据来自 `.obj` **文件**，顶点数由文件决定——一个稍精细的模型就会越过 1024，表现是「**模型缺一块**」，而且不报错、不打印，非常难查。

改成 `std::vector`：

```cpp
// ⚠ 第 12 步：顶点数不再写死上限。
//    之前是 `ClipVertex clip_vertices[1024]` 而且超了就静默截断……
//    改成 std::vector：上限交给内存，再也不用猜模型有多大。
std::vector<ClipVertex> clip_vertices(static_cast<std::size_t>(vertex_count));
```

**为什么这件事值得单独提**：`std::vector` 本身没什么技术含量，值钱的是**意识到「数据源变了，那些以前够用的常量假设就都不成立了」**。第 11 步的 `1024` 在当时是对的（顶点数自己数得清），第 12 步一换数据源就成了定时炸弹。这类「换数据源顺手拆掉的旧假设」，是工程里最容易漏、也最容易出事的一类修改。

## 八、自测题

1. `.obj` 里 `f 5/2/9` 的三个数字分别是什么？它们之间有对应关系吗？
2. `f -1 -2 -3` 是什么意思？
3. `f 1//7 2//8 3//9` 这种写法里，中间为什么是空的？解析时怎么处理？

### 10.1 为什么 OBJ 用三条索引，而 GPU 只要一条

**① 问题**

OBJ 里一个角写 `5/2/9`——位置、UV、法线各查各的表。看起来挺灵活。那为什么我们的 `Mesh`（以及所有 GPU）非要把它**拆开重绑**成「一个顶点 = 位置+UV+法线」的单一索引？直接用三条索引不行吗？

**② 直觉：问题不在「能不能存」，在于「能不能」**

先分清两件事：

| | 存储（存得下吗） | 处理（GPU 能不能干） |
| :--- | :--- | :--- |
| **三条索引** | 存得下，而且更省——`v` 表 8 个、`vt` 表 24 个、`vn` 表 6 个 | **不行** |
| **一条索引（de-indexed）** | 冗余——同样的位置可能存好几遍 | 行 |

关键在右列。GPU 的**顶点着色器**（vertex shader）是「**一个顶点跑一次**」的，它的输入是「这个顶点的位置 + 法线 + UV + 其它属性」这一整包。**它没有「分三次去三张表里各查一次」的能力**——它是被硬件固化成「取一个顶点、算一次、往下发」的流水线。

**③ 推导：为什么「位置相同」的角必须是不同的顶点**

拿一个**立方体**算一遍，一切就清楚了。

- 几何上有 **8 个位置**。
- 但每个位置是 **3 个面**的交汇点，每个面需要它自己的**法线**（三个面法线不同：比如角点 `(1,1,1)` 处，+X 面的法线、+Y 面的法线、+Z 面的法线各不相同）。
- 每个面还各要一份自己的 **UV**（每个面的贴图从 `(0,0)` 铺到 `(1,1)`，不在面与面之间连续）。

所以这个位置要 **3 份**顶点，每份的法线/UV 不同。8 × 3 = **24 个顶点**。

```
位置 (1,1,1) 上，一个角的三种「身份」：

  属于 +X 面 → 顶点 A：位置(1,1,1)  法线(1,0,0)  uv(0,0)
  属于 +Y 面 → 顶点 B：位置(1,1,1)  法线(0,1,0)  uv(0,0)
  属于 +Z 面 → 顶点 C：位置(1,1,1)  法线(0,0,1)  uv(0,0)

  三个顶点位置完全相同，但属性不同 → 必须是三个独立顶点，不能合并
```

于是 de-indexing 的规则就一句话：

> **(v, vt, vn) 三元组相同 → 同一个顶点；只要有一个不同 → 不同顶点。**

这解释了为什么「去重」用**三元组**当 key，而不是用位置当 key——用位置去重就会把上面 A、B、C 合并成一个，于是立方体的棱角会变成圆滑的（法线被平均了），或者某个面的贴图错位。

**④ 它在管线里管哪一段 / 为什么绕不过去**

`Mesh` 的形态（一个顶点索引 + 一包属性）**就是** GPU 顶点着色器的输入形态。这一步换算不是「优化」，是**「把文件格式适配成硬件要求的格式」**——所以任何一个模型加载器（Assimp、Unity 的 ModelImporter、Unreal 的 FBX importer）内部都有这个 de-indexing 阶段。

搞错会怎样：

- 用**位置**去重 → 棱角被抹圆（法线被平均），或者贴图在面边界错位。
- 完全**不去重**（每个角都新建顶点）→ 也能画出正确的图，只是顶点数偏多、浪费。所以「去重」是优化，「按三元组去重」才既优化又正确。
- **忘了存 UV 或法线** → 输出顶点缺少对应属性，贴图全 `(0,0)`（整模型一个颜色）或法线全是零（光照全黑）。

### 10.2 为什么循环曲面必须多生成一圈顶点

**① 问题**

第 4 节说圆环的接缝暗带要靠「多生成一排顶点」解决。可这是为什么？明明`seg` 列就够把一圈走完了——第 `seg` 列回到第一列不就接上了吗？

**② 直觉：UV 是「每个顶点自带的一个数」，面与面之间靠插值**

先建立画面感。UV 不是「贴在三角形上的一张图」，而是「**每个顶点身上的一个坐标**」；三角形内部的 UV 是**从三个顶点的 UV 线性插值**出来的。

所以问题是：接缝处那一圈三角形，它的两个顶点各自的 `u` 是多少？

**③ 推导：拿 seg = 40 算一遍**

不加那一圈时，第 `i` 列（`i = 0..39`）的 `u = i / 40`：

```
第 0  列 → u = 0.000     ← 第一列
...
第 39 列 → u = 0.975     ← 最后一列
```

而第 39 列和第 0 列在**几何上是挨着的**（转一圈接上）。夹在它们之间那一圈三角形，两个顶点的 `u` 分别是 **0.975 和 0.000**。

插值器只看到「两个数」，它不知道「0.975 → 0.000」应该理解为「往前走 0.025」，它只会理解为「**倒着走 0.975**」。于是这一圈三角形把**整张贴图反向铺了一遍**——40 个像素的宽度里塞进整张图，又脏又暗，就是那条带。

**加一排之后**（第 40 列）：

```
第 39 列 → u = 0.975
第 40 列 → u = 1.000   ← 位置和第 0 列重合（角度绕回来了），但 u 是 1.0
```

夹在 39 和 40 之间那一圈，`u` 从 0.975 走到 1.000——只走 0.025，正常铺贴图。**接缝从「倒流一整张图」变成了「正常的一列」**。

**为什么不能把 u 钳到 1.0 或者用 clamp 采样**：

- **钳 u**：`u = 1.0` 和 `u = 0.0` 仍然差 1.0，问题原封不动。
- **采样时 clamp 而不是 wrap**：那样只影响**贴图边界之外**的采样，接缝处两个顶点都还在 `[0,1]` 内，clamp 拦不住。
- **多生成一排位**：唯一承认「同一几何位置、两种 UV」的做法——回到了 10.1 的结论：**顶点 = 属性的组合**。位置一样但 UV 不同，就该是两个顶点。

**④ 它在管线里管哪一段 / 会反复用到**

这条规则管的是**「数据生成」**阶段（生成模型的那一步），不是渲染管线本身。它会反复出现：

| 曲面 | 要多半圈的方向 |
| :--- | :--- |
| 圆环 | 大圈（`u` 方向）和小圈（`v` 方向）都要 |
| 球 | 经度方向（`u`）；纬度方向（`v`）到了极点本来就有退化三角形 |
| 圆柱 | 圆周方向（`u`） |
| 管状 / 环状扫掠 | 闭合方向 |

球的两极还有个小细节：`theta = 0` 和 `theta = π` 处，一整圈顶点**位置重合**（都在极点），夹出来的三角形是**退化的**（面积为零）。生成器顺手把它们跳过（[gen_obj_models.py](file:///d:/SDL_project/softbymyself/tools/gen_obj_models.py#L115-L117)）——退化三角形画不出像素，留着只是白算。

### 10.3 为什么 OBJ 的 `vt` 要翻转

**① 问题**

加载器里有一行 `uvs.emplace_back(u, 1.0f - v)`。为什么平白无故要 `1 - v`？不翻会怎样？

**② 直觉：UV 的「原点」没有全球统一标准**

「原点在哪」是个**约定**，历史上两条路线并行：

| 约定 | 原点 | v 增大方向 | 代表 |
| :--- | :--- | :--- | :--- |
| 图片传统（OBJ、大多数图片格式） | **左下角** | 向上 | OBJ / OpenGL |
| 屏幕传统（本项目 `Texture`、D3D 纹理） | **左上角** | 向下 | DirectX / 本项目 |

两条都没错。错的是**把两边混着用**。

**③ 推导：拿一个角算一遍**

设 OBJ 里有一个 UV 是 `vt 0.25 0.75`。它想说的是「**从下往上 75% 的位置**」——也就是靠近图片**顶部**。

本项目的 `Texture` 收到 `(u, v)` 后用 `y = v * height` 直接当行号，而**行号 0 是最上面一行**。所以：

```
不翻：  v = 0.75 → 行号 0.75 * H → 图片下部 3/4 处（错了，应该是顶部 3/4）
翻转：  v = 1 - 0.75 = 0.25 → 行号 0.25 * H → 图片上部 1/4 处 ✓（正是「从下 75%」= 从上 25%）
```

**④ 它在管线里管哪一段 / 搞错会怎样**

它管的是**「文件约定」→「本项目约定」的边界换算**，只该在加载器里做一次，翻完就统一了（[objloader.cpp](file:///d:/SDL_project/softbymyself/src/io/objloader.cpp#L100-L103)）。翻完的 UV 进到 `Mesh`、进到 `Texture`，全都是「左上角原点、v 向下」，后面再也不用管。

搞错会怎样：

- **不翻** → 整张贴图**上下颠倒**。注意：如果贴图本身上下对称（比如棋盘格），你**看不出来**；换一张上下不对称的（木纹、人脸、有字的海报）立刻穿帮。所以这类 bug 容易藏到很久以后才爆。
- **翻两次** → 又颠倒了（一个偶数次翻转 = 没翻）。表现为「明明我翻了怎么还是反的」，通常是「加载器翻了一次、材质系统又翻了一次」。

这也是为什么 [texture.hpp](file:///d:/SDL_project/softbymyself/src/core/texture.hpp#L11-L15) 特意把这个约定**写死在注释里**：

> 「这里把这层约定收在 Texture 内部，外面只管 u、v 落在 [0,1]……」

约定差这种东西，**唯一安全的做法是找一处写死、全项目遵守，并且写清楚**。任何「这里翻一下、那里翻一下」的项目最后一定会在某个角落翻错。
