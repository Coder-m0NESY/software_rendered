1. 视图矩阵到底要干什么

场景里的物体坐标都记在世界空间里。但渲染的时候，我们希望相机在主位上——让计算简单。

所以要把所有点搬到视空间（也叫相机空间），这个空间有三个约定：

  1. 相机在原点 (0,0,0)
  2. 相机朝 −Z 看（所以视野内的点 z 都是负的）
  3. +X 是右、+Y 是上（右手系）

干这件事的矩阵就是 视图矩阵 V，它的输入是相机的三个参数：

// 相机在哪
Vec3 eye;
// 相机看向哪个点
Vec3 target;
// 世界上方是哪个方向（用来定"头顶朝哪"，一般 (0,1,0)）
Vec3 up;
为什么 up 不能省？ 光有「眼睛」和「看的目标」，相机还能绕自己的视线轴自由旋转（头歪着看）。up 就是用来定「头顶朝哪」的，它把最后一个自由度钉死。

2. 第一步：反过来想

直接想「怎么把整个世界的点搬到相机坐标系」很难。

反过来想就简单了：怎么把相机搬到原点、并摆正？

这个变换好写，因为相机的姿态是「已知的」——就是我们手上的 eye / target / up。写成两步：

1

旋转：把相机转到与世界轴对齐（前 = −Z，上 = +Y，右 = +X）

2

平移：把相机从 eye 挪到原点，也就是平移 −eye

记这个「相机 → 原点」的矩阵为 M_cam。我们真正要的视图矩阵 V，就是把世界变得和相机一致，所以：

V = M_cam 的逆
核心思想 视图矩阵 = 「相机摆正」这个变换的逆。
这个「反过来想」的技巧在图形学里到处都是——世界→相机的矩阵，就是相机→世界的矩阵求逆。

3. 第二步：算出相机的三个轴

要写「把相机转到与世界轴对齐」的矩阵，先得知道相机自己的三个轴在世界空间里是什么方向。

相机自己的三个轴叫 f（forward，前方）、s（side，右方）、u（up，上方）：

三个轴这样算——顺序不能换：

// ① 前方：从眼睛指向目标，归一化
Vec3 f = normalize(target - eye);

// ② 右方：前方 与 世界上方 的叉积
Vec3 s = normalize(cross(f, up));

// ③ 上方：右方 与 前方 的叉积（注意参数顺序和 ② 相反）
Vec3 u = cross(s, f);

为什么要用叉积？

因为相机的三个轴必须两两垂直。而叉积的性质正好是：

a × b 的结果同时垂直于 a 和 b

  • f × up 垂直于 f 和 up。垂直于 f 意味着它在「与视线垂直的平面」里；取叉积后，s 一定和视线垂直——正是「右方」该有的样子。
  • s × f 垂直于 s 和 f，自然就是「上方」。

为什么 u 不用归一化？

因为 f 和 s 已经满足：

  • 都是单位向量（归一化过了）
  • 互相垂直（s 是叉积出来的，必然垂直 f）

两个垂直的单位向量，叉积出来的结果长度也正好是 1。所以 u 天生就是单位向量，不用再归一化。

为什么 ② 里的 up 需要「掰正」？ 传进来的 up（比如 (0,1,0)）只是「大概朝上」，它不一定和 f 垂直。你歪着头看东西时，头顶方向就不是垂直于视线的。
叉积 f × up 的作用正是：把不垂直的 up 校正成真正垂直的方向。这就是为什么参数里传 up 而不是直接传 u。

4. 第三步：旋转部分

这里是整个 lookAt 里最容易卡住的一步。你手上明明只有三条箭头，怎么就变成一个矩阵了？中间发生了什么？

把它拆成五个小问题，一个一个来。跳着看也没关系，每一小节都是独立的。

4.1 地基：矩阵乘向量，本质是「三次点积」

所有困惑都从这儿开始。矩阵乘向量不是「把数字搬来搬去」，它的定义就是：拿矩阵的每一行，去和向量做一次点积。

那「点积」又是什么？点积 = 投影长度。

dot(s, p)  =  p 在 s 方向上「投影」了多长
把两件事合起来（这条一定要记住）
矩阵的第 i 行如果填的是某个方向 a，那么输出向量的第 i 个分量，就是「输入向量在 a 方向上投影了多长」。

换成大白话：填一行，就等于在问「这个点在这个方向上有多远」。

4.2 我们要的效果是什么

回到目标。相机自己的三个轴，在世界里是三个方向：

相机轴含义应该变成视空间的哪个轴
s相机的右+X
u相机的上+Y
−f相机的后+Z  ← 注意是负的 f

为什么是 −f？因为相机朝 f 看，而视空间里相机朝 −Z 看。所以视空间的 +Z 指向相机背后，正好是 −f。

翻译成人话，就是三句话：

  • 「一个点在相机右边多远」 → 成为它的 x 坐标
  • 「一个点在相机上方多远」 → 成为它的 y 坐标
  • 「一个点在相机后方多远」 → 成为它的 z 坐标

4.3 「填行」为什么正好能做到这件事

现在把 4.1 那句话搬过来：

填一行 = 问「这个点在这个方向上投影多长」

所以我们把 s 填进第 0 行，那么输出的第 0 个分量就自动是「该点在 s 方向上的投影」——也就是「在相机右边多远」，正好就是我们要的 x 坐标！

三个轴各自填一行，就成了：

s.xs.ys.z0 u.xu.yu.z0 −f.x−f.y−f.z0 0001

但这还只是「听起来有道理」。我们来做个验收测试：把相机自己的右方向 s 代进去，看输出到底是什么。

M · s = ( 第0行·s,      第1行·s,      第2行·s )
      = ( dot(s, s),    dot(u, s),    dot(−f, s) )

关键来了：这三个点积分别是多少？

答案是确定的，因为我们早就知道一件事——三个轴两两垂直，而且都是单位长度。

点积值为什么
dot(s, s)1自己和自己，且 s 是单位向量
dot(u, s)0垂直（夹角 90°，cos 90° = 0）
dot(−f, s)0垂直

所以那个验收测试的结果是：

M · s = (1, 0, 0)      ← 相机的「右」，被送到了视空间的 +X ✅

同样地，另外两条轴也一样：

M · u  = (0, 1, 0)     ← 相机的「上」 → +Y ✅
M · w  = (0, 0, 1)     ← 相机的「后」 → +Z ✅
这就是「填行」的全部理由
因为点积在「同一个向量」时是 1、「垂直向量」时是 0，所以每一行都只认自己那个轴，把另外两个轴自动忽略掉。

三条轴因此被各自送到了对应的坐标轴上——这正是 4.2 里我们要的效果。

反过来说：如果三个轴不正交，这张表就不成立了，映射就会歪掉，整个世界被剪切变形。这就是上一节反复强调「必须垂直」的原因。

4.4 为什么不能填「列」

同样的九个数字，横着摆和竖着摆，得到的是互为反向的两个变换。

为什么填行就等于填列的转置？因为：

旋转矩阵的逆  =  它的转置        （因为三个轴正交）

而「相机 → 世界」的逆，正是「世界 → 相机」——我们想要的那个。

填错的症状
填成列，画面不会变成全黑，而是整个场景往反方向跑：你鼠标往左拖，画面往右转。
这个错误很难一眼看出来，因为画面确实「动了」，只是方向不对。如果出现这种诡异情况，先回来查这一条。

4.5 换个说法：三把尺子

如果上面还没完全消化，用这个比喻再走一遍。

把矩阵的三行想成三把尺子：

  • 第 0 行，是一把沿 s 方向摆的尺子（朝着相机右边）
  • 第 1 行，是一把沿 u 方向摆的尺子（朝着相机上方）
  • 第 2 行，是一把沿 −f 方向摆的尺子（朝着相机后方）

一个点 p 进来，三把尺子各量它一次：

第 0 行量出：p 在「相机右边」方向上有多少   →  x
第 1 行量出：p 在「相机上方」方向上有多少   →  y
第 2 行量出：p 在「相机后方」方向上有多少   →  z

量完，p 在相机坐标系里的三个坐标就都有了。就这么简单。

所以「填行」不是背下来的规则
它是点积的几何意义（投影）加上三个轴的正交性，两者一凑必然得出的结果。
理解到这一层，就不用记「填行还是填列」了——你可以自己推。

回到第一行的验收：它算 dot(s, p)，就是「点 p 在 s 方向上的投影长度」，也正是 p 在新坐标系里的 x 坐标。✅

5. 第四步：平移部分

平移要「把相机搬到原点」，也就是减去 eye。但顺序很关键：

先旋转，再平移
正确顺序是 V · p = R · (p − eye)，不是 R · p − eye。

为什么？因为旋转是绕原点的。如果先减去 eye（平移），再旋转，那就变成绕世界原点转了，相机的位置就错了。

展开一下，把平移项整理进矩阵的第四列：

V · p = R · (p − eye)
      = R · p  −  R · eye

其中 R · eye 是什么？eye 乘上旋转矩阵，就是「把 eye 投影到相机的三个轴上」：

dot(s, eye) dot(u, eye) −dot(f, eye)

所以平移列就是它取负：

−dot(s, eye) −dot(u, eye) dot(f, eye)

第三行的符号「翻」了一次（−dot(f, eye) 变成 dot(f, eye)），是因为第三行本身就带负号（−f）。负负得正。

6. 合起来：完整矩阵

旋转部分填前三列，平移部分填第四列：

s.xs.ys.z−dot(s,eye) u.xu.yu.z−dot(u,eye) −f.x−f.y−f.zdot(f,eye) 0001

这就是全部。没有魔法，就是三个轴 + 一个平移。

7. 代码逐行对照

对应 src/math/mat.hpp 里的实现：

inline Mat44 Mat44::lookAt(const Vec3& eye, const Vec3& target, const Vec3& up)
{
    // 相机自己的三个轴，在「世界空间」里表示出来
    Vec3 f = normalize(target - eye);   // 前方
    Vec3 s = normalize(cross(f, up));   // 右方（用叉积把 up 掰正，保证与 f 垂直）
    Vec3 u = cross(s, f);               // 上方：f、s 已是单位且垂直，u 自然也是单位向量

    // 旋转部分：把相机轴填进矩阵的行里，等于让世界「反向旋转」
    // 平移部分：把相机位置搬到原点，所以是 -dot(轴, eye)
    Mat44 r = identity();
    r.m[0][0] =  s.x; r.m[0][1] =  s.y; r.m[0][2] =  s.z; r.m[0][3] = -dot(s, eye);
    r.m[1][0] =  u.x; r.m[1][1] =  u.y; r.m[1][2] =  u.z; r.m[1][3] = -dot(u, eye);
    // 第三行取负号：相机是朝 -Z 看的，所以世界的 -f 才是视空间的前方
    r.m[2][0] = -f.x; r.m[2][1] = -f.y; r.m[2][2] = -f.z; r.m[2][3] =  dot(f, eye);
    return r;
}
注意 m[行][列] 本项目用行主序。m[0][3] 是第一行第四列，也就是平移的 x 分量——不是第四行第一列。

8. 拿数字验证一遍

最简单的一组：相机站在 (0,0,3)，看向原点，up = (0,1,0)。

① 算三个轴

f = normalize((0,0,0) − (0,0,3)) = normalize((0,0,−3)) = (0, 0, −1)

s = normalize(cross(f, up))
  = normalize(cross((0,0,−1), (0,1,0)))
  = normalize(( 0·0 − (−1)·1 ,  (−1)·0 − 0·0 ,  0·1 − 0·0 ))
  = normalize((1, 0, 0)) = (1, 0, 0)

u = cross(s, f)
  = cross((1,0,0), (0,0,−1)) = (0, 1, 0)

② 填矩阵

dot(s, eye) = (1,0,0)·(0,0,3) = 0
dot(u, eye) = (0,1,0)·(0,0,3) = 0
dot(f, eye) = (0,0,−1)·(0,0,3) = −3
1000 0100 001−3 0001

③ 检查结果是否合理

拿世界原点 (0,0,0) 试一下：

V · (0,0,0,1) = (0, 0, −3, 1)

🔍 世界原点在视空间里的 z = −3，正好是「在相机前方 3 个单位」。✅

再拿相机的眼睛位置 (0,0,3) 试：

V · (0,0,3,1) = (0, 0, 0, 1)

🔍 相机自己被搬到了原点。✅ 这正是视图矩阵的定义。

自己验一遍的方法
1. 把 eye 代进 V，结果必须是原点
2. 把 target 代进 V，z 必须是负数（在相机前方），x、y 必须是 0（正对着看）
这样两下就能确认 lookAt 写对了。

10. 三个常见坑



坑一：up 和视线平行



如果 up 和 f 平行（比如相机垂直向下看，而 up 还是 (0,1,0)），那么：



cross(f, up) = (0,0,0)



叉积是零向量，归一化时除以零长度，得到 (0,0,0)，整个矩阵塌掉。



处理：相机俯仰角别到 90°，或者换一个不平行于视线的 up。



坑二：把轴填成列，而不是行



填成列得到的是转置，也就是「相机 → 世界」。现象是：相机绕着自己反向转，整个场景看起来在往反方向跑。这个错误很难一眼看出来，因为画面「动了」，只是方向不对。



坑三：忘了「先旋转、再平移」



写成 R · p − eye 而不是 R · (p − eye)，物体会绕着错误的中心转。



矩阵形式下这个坑不那么容易踩（因为平移列是 −dot(轴, eye) 算出来的），但如果你手动分两步做变换，就要注意了。




  顺带一提：手性
  本教程用右手系、相机朝 −Z。如果是 DirectX 那套左手系（相机朝 +Z），第三行不用取负，而且背面剔除的绕序判断也会反过来。别混用。
