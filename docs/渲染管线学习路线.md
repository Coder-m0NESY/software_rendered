## 一、管线全图（对照那张图）

一帧画面从 CPU 到屏幕，代码执行顺序如下。红框里的四个阶段是**手写渲染器的核心**：

```
CPU 应用阶段 ──► 顶点处理 ──► 光栅化操作 ──► 片元处理 ──► 输出合并 ──► 帧缓冲
                  └──────────── 红框 ────────────┘
```

| 阶段 | 子步骤 | 一句话解释 |
| :--- | :--- | :--- |
| **CPU 应用阶段** | 视锥体剔除 | 丢掉压根不在相机视野内的物体 |
| | 渲染排序 | 决定先画谁后画谁（不透明物体通常无所谓，透明物体必须从远到近） |
| | 提交 Drawcall | 把「画哪些顶点」打包交给下一阶段。GPU 上是一次驱动调用；软件渲染器里就是一个函数调用 |
| **顶点处理** | 顶点 MVP 变换 | 把顶点从模型空间搬进裁剪空间 |
| | 自定义数据 | 每个顶点额外携带的信息：UV、法线、颜色 |
| **光栅化操作** | 裁剪 | 丢掉落在相机背后、或超出视锥的图元 |
| | NDC | 透视除法，得到归一化设备坐标 |
| | 背面剔除 | 丢掉看不见的那一半三角形 |
| | 屏幕坐标 | 把 NDC 的 `[-1,1]` 映射到像素的 `[0,width]` |
| | 图元装配 | 把顶点组装成三角形/线段 |
| | 光栅化 | 判断哪些像素被三角形覆盖 |
| **片元处理** | 光照着色 | 按法线和光源算明暗 |
| | 纹理着色 | 采样纹理贴图 |
| **输出合并** | Alpha 测试 | 透明度低于阈值直接丢弃片元 |
| | 模板测试 | 用掩码控制哪些像素能写（本项目不做） |
| | 深度测试 | 谁在前面画谁 |
| | 颜色混合 | 半透明物体的混色 |
| **帧缓冲** | 颜色缓冲 | 一张像素画布（已有） |
| | 深度缓冲 | 每个像素记一个深度值（**还没建**） |

## 三、每个阶段要学什么、怎么验

### 阶段 1：CPU 应用阶段

**要懂的概念**

- **视锥体（Frustum）**：相机能看到的那块空间，是一个被 6 个面切出来的四棱锥台。判断「物体在不在视锥里」通常用包围盒（AABB / 包围球）快速排除。
- **为什么先剔除**：后面的每个阶段都贵，能提前丢掉的绝不留到光栅化。
- **排序**：不透明物体谁先画都行（有深度测试兜底）；**透明物体必须从远到近**，否则混色顺序错。

**在项目里对应**：最容易被忽略的一段。`Scene` 结构（README 里提到「一堆模型 + 一个相机 + 一个光源」）就应该在这一层做剔除和排序。

**验证**：给场景放 100 个立方体，只留 3 个在视野里，对比「剔除前 vs 剔除后」的帧时间。

---

### 阶段 2：顶点处理

**要懂的概念**

- **四种坐标空间**：模型空间 → 世界空间 → 视空间 → 裁剪空间。每换一次空间乘一个矩阵。
- **MVP = P · V · M**，作用顺序是从右往左：`clip = P * V * M * v`。
  - `M` 模型矩阵：把顶点从模型自己的坐标系摆到世界
  - `V` 视图矩阵：把世界搬到「相机在原点、朝 −Z 看」的坐标系
  - `P` 投影矩阵：把视锥压成 NDC 立方体
- **齐次坐标 + w**：投影矩阵不给 x、y 做除法，而是把 `−z` 塞进 `w`，留给下一步的透视除法统一处理。这是整个管线最精妙的一处设计。
- **自定义数据**：顶点不该只有位置，还要有 UV、法线。它们跟位置**一起**被变换（法线要用逆转置矩阵，但初学可以先不做非均匀缩放）。

**在项目里对应**：第 3 步。你需要一个顶点结构体：

```cpp
struct Vertex {
    Vec3 position;
    Vec3 normal;
    Vec2 uv;
};
```

**验证（正合文档说的「只能读数字」）**：先别画，把立方体 8 个顶点乘完 MVP 后的结果 `printf` 出来。检查：

- 近的顶点 `w` 小、远的顶点 `w` 大（在相机朝 −Z 时，`w = −z`）
- 除以 `w` 后，x、y 都落在 `[-1, 1]`

**常见坑**

- 「先使用后定义」是 C++ 里最容易犯的一类错：`Mat33` 里曾经引用了还没定义的 `Mat44`，编译不过。修法是**把 `Mat44` 的定义提到 `Mat33` 前面**（本项目就是这么改的），或者加前置声明 `class Mat44;`。
- 矩阵行主序 / 列主序搞反：乘出来的点会「转错方向」，而且很难看出是序的问题。**固定一种约定，全项目统一**。

### 阶段 3：光栅化操作

这是子步骤最多的一段，逐个来。

#### 3.1 裁剪（Clipping）

**要懂的概念**

- 为什么必须裁：透视除法要除以 `w`，而相机背后的点 `w ≤ 0`，除下去坐标会**翻转到屏幕另一侧**，画出穿屏的鬼畜三角形。
- **近平面裁剪最关键**。完整裁剪是 Sutherland-Hodgman 算法，用 6 个面对多边形逐个裁剪——代码量不小。**初学者可以先只裁近平面**（`w > near`），能解决 90% 的穿屏问题。

**验证**：把相机推到贴着立方体，画面不应该有三角形乱飞。

#### 3.2 NDC（透视除法）

**要懂的概念**

```
ndc = (x/w, y/w, z/w)
```

这一步才真正产生「近大远小」。当前 `Vec4::perspectiveDivide()` 是**空函数**，需要补上（记得防 `w == 0`）。

**常见坑**：`z` 在透视除法后是**非线性**的，近处精度高、远处精度低。软件渲染器常直接用 `1/w` 当深度，简单又线性。

#### 3.3 背面剔除（Back-face Culling）

**要懂的概念**

- 一个封闭物体的背对相机的面，永远看不见，可以扔掉一半。
- **不用真的算法线**：把三角形投到屏幕后，算它三个点的**有向面积**（二维叉积）。符号为正/为负分别代表正面/背面，取决于你定的**绕序**（顺时针 or 逆时针）。

```cpp
// 屏幕空间有向面积，正负即朝向
float area = (x1 - x0) * (y2 - y0) - (x2 - x0) * (y1 - y0);
```

这一步顺便解决了「背面剔除：为什么不需要真的算法线？」那个问题。

#### 3.4 屏幕坐标（视口变换）

**要懂的概念**

```
sx = (ndc.x + 1) * 0.5 * width
sy = (1 - ndc.y) * 0.5 * height   // 注意 y 要翻转：NDC 向上为正，屏幕向下为正
```

**常见坑**：忘了翻转 y，画面上下颠倒；忘了处理 `width/height`，画面被拉伸成非等比。

#### 3.5 图元装配

把顶点按索引拼成三角形。`Mesh` 要存「顶点数组 + 索引数组」。

#### 3.6 光栅化

**要懂的概念**

- **边函数（Edge Function）**：对三角形每条边算一个函数，三个都同号就在三角形内。它本质是 3.3 里那个有向面积的推广。
- 边函数还有个妙用：三个值归一化后**就是重心坐标**，可以直接拿来插值顶点属性——这正对应文档里「为什么用边函数，不用扫描线？」那题的答案。
- 先做**包围盒 + 逐像素**的朴素版本，别一上来就写扫描线优化。

**验证**：画一个纯色三角形，三个顶点分别在屏幕三个角。

---

### 阶段 4：片元处理

#### 4.1 光照着色

**要懂的概念**

- **Lambert 漫反射**：`亮度 = max(0, dot(法线, 光照方向))`。法线必须是**单位向量**，否则亮度算错——这就是 `Vec3::length_squared()` 漏了 `z` 会致命的原因。
- 法线要跟着模型矩阵一起变换（正确做法是**逆转置矩阵**）。

#### 4.2 纹理着色

**要懂的概念**

- **UV 采样**：UV 在 `[0,1]`，乘纹理宽高得到像素坐标。
- **透视校正插值**：屏幕上等长的一段，在世界里**并不等长**。直接线性插值 UV 会让远处的纹理被拉伸扭曲。正确做法是插值 `uv/w` 和 `1/w`，再相除：

```
uv = (uv/w 的插值) / (1/w 的插值)
```

这正对应文档里「透视校正：为什么贴图必须除以 w？」那题。

- **最近邻 vs 双线性**：先用最近邻跑通，再升级双线性。

**验证**：地板上铺棋盘格，近处格子大、远处格子小且不扭曲。

### 阶段 5：输出合并

#### 5.1 Alpha 测试

透明度低于阈值（比如 0.5）的片元直接丢弃，不写颜色也不写深度。用来做「镂空」效果。

#### 5.2 深度测试

**要懂的概念**

- 标准做法：每个像素存一个深度，新片元的深度比已存的更近才覆盖。
- 存 `1/z` 而不是 `z`：透视除法后 `z` 非线性，而 `1/z` 是**线性可插值**的，精度分布也更合理。这正对应文档里「为什么近处的精度比远处高？」那题。
- 深度缓冲要和颜色缓冲**同尺寸**，且**每帧清空**。

**在项目里对应**：第 6 步。README 的模块表早就写了「PixelBuffer = 一块颜色数组 **+ 一块深度数组**」，但代码里 `PixelBuffer` **目前只有颜色**。建议早点补上 `std::vector<float> depth_`，别等到第 6 步再改所有写像素的接口。

**验证**：转立方体时，后面的面不会盖住前面的面。

#### 5.3 颜色混合

```
输出 = 源颜色 * α + 目标颜色 * (1 − α)
```

半透明物体必须**从远到近**绘制（回到阶段 1 的排序问题）。

## 五、执行顺序

分成四个阶段。**每个阶段结束都要有一个能看见的结果**，不要把功能攒到最后一起调。

```
阶段 A：打地基      1 → 2 → 3 → 4        修已有代码，不产生画面
阶段 B：第一个立方体 5 → 6 → 7 → 8        从打印数字到看见实心立方体
阶段 C：让它好看     9 → 10               光照 → 纹理
阶段 D：补齐管线     11 → 12 → 13         剔除 / 裁剪 → .obj → 混合
```

### 阶段 A：打地基（1–4）

| # | 做什么 | 动哪些文件 | 怎么算做完 |
| :---: | :--- | :--- | :--- |
| 1 | 让 `mat.hpp` 能编译：把 `Mat44` 的定义提到 `Mat33` 之前；补齐 `perspective` / `lookAt` / `translate` / `rotateX/Y/Z` 的实现 | `src/math/mat.hpp` | `Ctrl+Shift+B` 编译通过，零报错 |
| 2 | 补上空函数 `Vec4::perspectiveDivide()`：除以 w，并防 `w == 0` | `src/math/vec.hpp` | 编译通过 |
| 3 | 修 `Vec3` 两个 bug：`length_squared()` 补 `z*z`；`cross()` 改成返回 `Vec3` 并算完整 3D 叉积 | `src/math/vec.hpp` | `Vec3(0,0,5).length()` 得到 5（**现在是 0**） |

- 第 1 步：`mat.hpp` 现在是**先使用后定义**，编译不过。不修的话，第 5 步连试都试不了。
- 第 3 步：`lookAt` 要算 `cross(forward, up)`，而 `cross()` 现在返回 `float`，**类型对不上，直接编译失败**。所以第 3 步必须排在第 5 步之前。
- 第 4 步：深度数组越晚加越痛。到第 8 步才加的话，前面所有写像素的调用点都要改一遍。

| :---: | :--- | :--- | :--- |

**第 11 步内部也有顺序**，从易到难：

1. **背面剔除**——最简单，屏幕空间有向面积，十几行代码
2. **视锥体剔除**——中等，要算六个平面 + 包围盒求交
3. **裁剪**——最难，Sutherland-Hodgman 算法。**可以只做近平面**，先跑通

**第 12 步为什么排这么后？**

因为前面一直在手写立方体——顶点少、格式你自己定的，出了错能自己排查。等管线完全跑通、画面也对了，再换成真模型。这时候如果出问题，**那就一定是 objloader 的锅**，不用怀疑别处。

反过来，如果一开始就用 `.obj`，一旦画面不对，你连是加载错了、还是矩阵错了都分不清。

### 三条铁律

**1. 先看数字，再看画面。**

矩阵、坐标变换这类东西，`printf` 出来的数字比画面可靠得多。画面只能告诉你「不对」，数字能告诉你「哪里不对」。

**2. 一次只做一件事，做完必须有能验证的结果。**

不要「顺手把光照也写了」。上面每个步骤的「怎么算做完」那一栏就是验收标准——没达到就别往下走。

**3. 卡住时，先确认是哪一层错了。**

画面不对时，按 **6.7 节「症状 → 查哪个文件」**那张表去定位。不要一头扎进 `rasterizer.cpp` 里乱改——很可能问题根本不在那儿。

> 注意：第 9、10 步和原文档的第 7、8 步**顺序调换了**。原文档是「先纹理后光照」，这里改成「先光照后纹理」，理由见上表。其余步骤和原文档一致。

## 六、目录讲解：为什么这么摆，每个文件是什么

### 6.1 唯一的摆放原则

**按「离硬件有多远」分层，不要按「功能」分层。**

新手最容易按功能分：建一个 `三角形/` 放光栅化、一个 `光照/` 放光照、一个 `模型/` 放读模型。这样分，写着写着就变成：

- 光照需要知道相机在哪 → `光照/` 得 include `相机/`
- 相机需要知道窗口多大 → `相机/` 得 include `窗口/`
- 窗口又要用来显示光照结果 → `窗口/` 得 include `光照/`

**转了一圈，互相 include，成了环。** 这时候改任何一个文件，都可能崩掉另外两个，而且你根本不知道是谁依赖谁。

所以整个项目只有一条硬规则：

> **一层的代码，只允许 include 它下面那层。永远不许反向。**

只要守住这条，依赖图就永远是一个**单向的、没有环的**结构，任何一处改动的影响范围都只往一个方向扩散。

### 6.2 五个目录分别是什么

把渲染一帧想象成一条**流水线**，五个目录就是从最底层到最上层：

| 目录 | 是什么 | 回答的问题 | 它允许 include 谁 |
| :--- | :--- | :--- | :--- |
| `core/` | 底层零件 | 像素存在哪？怎么送到屏幕上？ | 谁也不依赖 |
| `math/` | 数学工具 | 向量、矩阵怎么算？ | 谁也不依赖 |
| `scene/` | 场景数据 | 场景里都有些什么东西？ | `core`、`math` |
| `render/` | 渲染算法 | 怎么把这些东西画出来？ | `core`、`math`、`scene` |
| `io/` | 文件读写 | 这些数据是从哪儿来的？ | `scene` |

**为什么 `core/` 和 `math/` 谁都不依赖？**

因为它们是最底层的零件，本身就不知道「渲染」这件事存在：

- `Color` 只知道「我有 r、g、b、a 四个数」，它不知道屏幕有多大
- `Vec3` 只知道「我有 x、y、z」，它不知道什么叫三角形

它们不知道上面在干什么，所以上面所有东西都能安全地用它俩。这就是「底层稳定」的含义。

**为什么 `io/` 要单独一个目录，不塞进 `scene/`？**

因为它是**全项目唯一会碰硬盘**的模块，也是唯一会**失败**的模块（文件不存在、格式写错、数字解析不了）。把它关在一个目录里有两层好处：

1. 想知道「这个项目读不读硬盘」，看一眼目录就知道
2. 将来要做「不读文件、直接在代码里造模型」，只要把这个目录排除掉

### 6.3 依赖长什么样

箭头表示「左边可以 include 右边」：

```
                    ┌──► io/objloader ──┐
main ───────────────┤                   ▼
                    └──────────►  scene  ──►  render  ──►  core
                                                        │
                                                        └──►  math
```

注意 `Window` 不在图里——它是特殊的一个。它是**唯一认识 SDL** 的模块，但它被 `main` 直接持有，不属于上面任何一层的数据流。`render/` 里的代码永远不知道 SDL 的存在，它只管往 `PixelBuffer` 里写数。

### 6.5 跟着一条数据走一遍

光看表格还是抽象，跟着一个顶点走一遍最清楚。假设你读进来一个立方体：

```
① 硬盘上的 cube.obj
      ↓  io/objloader.cpp        读文件、解析成顶点
② Mesh（顶点数组 + 索引数组）
      ↓  scene/scene.cpp         用 frustum 判断"在不在视野里"
③ 视锥剔除后的 Mesh 列表
      ↓  render/renderer.cpp     乘 M（摆到世界）、乘 V（搬到相机）、乘 P（压进裁剪空间）
④ 裁剪空间的顶点 (x, y, z, w)
      ↓  render/clipper.cpp      丢掉相机背后的三角形
⑤ 干净的多边形
      ↓  render/renderer.cpp     除以 w、换算成屏幕像素坐标
⑥ 屏幕上的三角形
      ↓  render/rasterizer.cpp   判断盖住了哪些像素；背面剔除；调 lighting 算明暗；调 texture 取颜色
⑦ 每个像素的颜色
      ↓  render/rasterizer.cpp   深度测试通过后，写进 PixelBuffer
⑧ PixelBuffer（颜色数组 + 深度数组）
      ↓  core/window.cpp         present() 贴到屏幕
⑨ 你眼睛看到的画面
```

**注意第 ③ 到第 ⑥ 步全都在 `renderer.cpp` 里串联**，但它自己不实现具体算法——具体算的活儿分别交给 `clipper` / `rasterizer` / `lighting`。这就是「串联」和「实现」的分工。

### 6.6 三道自测题

想验证自己是不是真的懂了这套分层，问自己三个问题：

**Q1：`math/vec.hpp` 能不能 include `core/color.hpp`？**

不能。`math` 在最底层，一层都不许往上依赖。如果哪天你在 `vec.hpp` 里写了 `#include "color.hpp"`，说明你把某一层的依赖搞反了。

**Q2：能不能在 `Mesh` 里加一个 `void draw()` 方法？**

不能。`Mesh` 属于 `scene`（有什么），`draw` 属于 `render`（怎么画）。`Mesh` 一旦有了 `draw()`，就等于它知道了像素、光栅化、甚至 SDL——就没法在没有屏幕的地方（比如将来做离线渲染存图）复用它了。

**Q3：`Rasterizer` 能不能持有 `Camera`？**

不能。`Rasterizer` 只该看到「屏幕上的三角形」和「像素坐标」，不该知道相机摆在哪、视锥多大。传给它的是已经算好的屏幕坐标，不是相机。

这三题答对了，说明你理解的是「依赖方向」，而不只是「文件放在哪个文件夹」。
